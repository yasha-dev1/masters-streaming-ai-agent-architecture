Companion to the Evaluation Protocol · 30 Aug 2026

Decisions, plan, and how each experiment is actually run

The protocol says what and why. This says which option was chosen, in what order the work happens, what a run consists of step by step, and — for every experiment — the checks that must pass before its numbers are believed.

DecisionsTwelve calls, made

D1
Corpus R = Apache Kafka, window 2026-01-01 → 2026-06-30.

Highest dev@ volume of the live-JIRA Apache projects, a KIP process whose [VOTE]/[DISCUSS] threads have unambiguous outcomes, active JIRA, and GitHub PRs with mandated KAFKA-N keys. Flink is the replication corpus if time remains, not a parallel primary. Jan–Apr is warm-up (the store is built), May–Jun is the probe period.

D2
Corpus S = OrgForge, added in Phase 2, extended with clicks and Stripe.

Phase 1 runs E1/E2/E3/E6 on Corpus R alone, because R needs no generator and produces the central E3 result. OrgForge is added for the customer-side claims (E1 injected situations, E4 simulated tasks, E6 load shapes). If Phase 1 slips, Phase 2 shrinks to E1-injected + E6 only — never dropped entirely, because E1 has no exact ground truth without it.

D3
Entity keys for R: issue:KAFKA-N, kip:N, pr:N, thread:<root-message-id>, contributor:<sha256(email)[:12]>, component:<jira component>.

Issues, KIPs and PRs are the entities humans reason about; threads without a key are entities of their own; contributors are hashed for privacy. Components give a coarse entity that aggregates many events — useful for testing multi-source probes.

D4
Models. Builder and read agent: claude-sonnet-5 for every arm of every sweep; claude-opus-5 additionally for the S3 store only (E3 model-tier check). Judge: a non-Anthropic frontier model, temperature 0. Same prompt/schema versions across arms, hashed and logged.

One fixed mid-tier model keeps the sweeps affordable and comparable; the frontier tier on the headline arm shows whether conclusions depend on model strength. Judge from a different family avoids self-preference bias.

D5
Fast-lane budget headline b = 2 %; sweep {1, 2, 5, 10} %. θ per source is tuned on Jan–Feb of the window and frozen before May–Jun is touched.

Tuning on the probe period would leak. 2 % is in the range where one on-call human could review admissions; the sweep shows the curve.

D6
Store layout for the curated arms = the seeded harnext layout (CLAUDE.md, INDEX.md, _meta/schema.md, _meta/superseded.md, entities/<type>/<slug>/{OVERVIEW,timeline,facts}.md, topics/). Backend: the git backend, one commit per run.

Already implemented and tested; git gives snapshot-at-T for free via git checkout <sha>, which the leakage gate and E3 health checkpoints need.

D7
Batch window = session window per entity: 30 s gap, 20-event cap, 120 s max age for replay at 60× real time; scaled proportionally at other speeds.

The classifier already implements exactly these three knobs. At 60× replay, 30 s ≈ 30 real minutes of inactivity, a natural conversation gap.

D8
Read budget for E2/E3 comparisons = 8k tokens headline; 2k and 32k as the curve. Enforced by truncating what the read agent may load, counted with the provider's tokeniser.

8k fits a fast-lane run; 32k is the point where long-context degradation is documented to begin; 2k tests whether OVERVIEW alone suffices.

D9
Sample sizes: 300 probes per corpus (60 per family); 150 fast tasks + 150 batch windows per corpus; 200 injected situations; 3 seeds for every LLM-built store; 3 runs per task for pass^3.

Paired power calculation for a 10-point effect at α 0.05 / power 0.8 gives ~150; families are balanced so no family dominates.

D10
Fast-lane SLO for E6 = p99 latency-to-agent-start ≤ 2 s at up to 1.5× the single-lane knee; batch-lane SLO = fold latency p99 ≤ 5 min and consumer lag not trending up.

2 s is far below any LLM call, so it isolates the engine; 1.5× the knee is the overload regime where a single lane's tail is known to collapse.

D11
Pre-registration = a dated eval/PREREG.md committed before the first full run, listing every condition, primary metric, threshold and exclusion rule; amendments appended, never edited.
D12
Two bugs fixed before any run: the builder's per-org lock must cover every writer (the MCP path constructed its own BuildRunner); and the builder prompt's "no shell" instruction must match the allowed tools — decision: allow Bash, read-only, sandboxed, and say so in the write-up.

A race on the live store would corrupt the very fidelity being measured; an instruction/tool mismatch makes the experimental condition undefined.

InfrastructureBuilt once, used by every experiment

The replay file and the clock

Every experiment consumes the same JSONL. A replay.py producer reads it and emits to cms.events.raw.v1 at a chosen speed-up (60× for builds, open-loop fixed rates for E6), stamping each event with intended_send_ts. A replay stops at a cutoff T when asked; the builder's snapshot after the last fold before T is the state "as of T". Because the store is git-backed, snapshot(T) is a commit SHA, recorded in replay/snapshots.csv as (T, sha, last_event_id).

Probe generation (E2, E3, E5)

probes/
  gen_extraction.py    # current value of a field: component, assignee, fixVersion, KIP status
  gen_temporal.py      # value of field f of entity e AS OF T, T sampled uniformly in probe period
  gen_update.py        # fields with ≥2 transitions in window: latest value + the superseded one
  gen_multisource.py   # issue↔PR↔thread↔KIP links from regex join on mandated keys
  gen_abstention.py    # fields/entities that do not exist in the window
→ probes/kafka.jsonl: {probe_id, family, entity, T, question, gold, gold_type, superseded_values[], source_event_ids[]}

Each probe records source_event_ids — the events from which the gold was derived — so the leakage gate and the human audit can trace it.

Graders

  • grade_exact.py — normalised exact match for fields and IDs (case, whitespace, ticket-key formats, version strings); returns 0/1 and the normalised strings so mismatches are inspectable.
  • grade_claims.py — gold decomposed into atomic claims once (LLM, then frozen and human-checked in the pilot); each claim checked against the answer by an entailment call from the judge model; returns claim-recall and claim-precision.
  • grade_links.py — set precision/recall of cited keys vs the join.
  • grade_action.py — field exact-match (assignee@k, component, duplicate-of) + fact coverage (required IDs present) + optional pairwise judge, position-swapped.
  • store_health.py — file/byte counts, over-cap files, INDEX resolution rate, dangling refs, MinHash near-duplicate facts, superseded-value leakage.

The leakage gate

assert max(event_time for e in delivered_to_builder_before(sha)) <= T
assert no token of probe.question appears only in events with time > T
log: probe_id, T, sha, last_event_id, pass/fail

Runs for every probe and every task; the pass count is reported in the thesis. A failure excludes the probe and is logged, never silently fixed.

E1

Routing under a budget — how it is run

No LLM in the loop. Corpus R with weak labels in Phase 1; Corpus S with exact injected labels in Phase 2.

  1. Build the weak-label model (R). Labelling functions over each event: jira_priority ∈ {Blocker, Critical}; subject matches [VOTE], [URGENT], CVE-, release blocker; committer replied within 1 h (derived from the reply graph, using the later event); issue resolved within 24 h; PR merged within 24 h of open. Fit a Snorkel-style label model; output a probabilistic label per event plus each function's estimated accuracy and coverage.
  2. Inject situations (S). From OrgForge's scenario config: dispute on a VIP account, production incident with paging, churn signal (plan downgrade after failed invoice), security report — ≥ 4 archetypes, ≥ 50 each, onset timestamps and cost weights recorded. Add hard negatives: benign volume spikes on the same entities, chit-chat bursts.
  3. Tune θ on the tuning slice (R: Jan–Feb; S: first 20 simulated days) to hit the budget b; freeze per-source θ, the absolute floor (events per 5-min bucket) and the two window lengths in PREREG.
  4. Replay the probe period through each router policy R0–R5 at each b, recording per event: score, lane, decision time, window ids. Same replay file, same order.
  5. Score. recall@budget and precision@budget per source; VUS-PR and affiliation P/R via the reference implementations; NAB under low-FN profile; detection delay per situation (onset → first fast admission on that entity).
  6. Robustness. Re-score after jittering onsets ±5 min and flipping 10 % of weak labels; re-score with a uniform-random scorer and an always-flag scorer.
  7. Harm check (Phase 2, needs a store): for each R4-promoted event, run the fast-lane task twice — at admission time and at that entity's next window close — and grade both with grade_action.py. Report the paired delta.
Validity checks — the evaluation is trusted only if
  • Label-model diagnostics show no single labelling function with estimated accuracy < 0.6 or coverage < 1 %; conflicts between functions are reported, and agreement between the outcome-based functions (reply-within-1h, resolved-within-24h) and the declared-priority function is stated as a number — this is the thesis's own measurement of priority-label noise.
  • The random scorer's precision@budget ≈ prevalence and its VUS-PR ≈ prevalence; the always-flag scorer's recall = 1 with precision = prevalence. If any metric ranks either near R4, that metric is dropped.
  • Injected situations are not trivial: R1 (rules-only) must not reach recall@2 % > 0.9 on them, otherwise the injections are too easy and are regenerated with subtler features.
  • θ was tuned only on the tuning slice: the PREREG commit predates the first probe-period run (git timestamps).
  • Metric implementations are validated on three hand-constructed toy series with known VUS/affiliation values before use.
E2

State fidelity — how it is run

Same read agent, same 8k read budget, different sources of truth to read from.

  1. Generate probes (300 per corpus, 60 per family) from the probe generators; freeze probes/kafka.jsonl with its hash in PREREG.
  2. Materialise each arm at each probe's T: A1 = last-N events of the entity before T from the replay; A2 = BM25 index over all events before T; A3 = embedding index over the same; A4 = git checkout snapshot(T) of the store. A0 receives nothing.
  3. Ask. One read-agent run per (probe, arm): system prompt "answer from the provided material only; say UNKNOWN if not present; cite IDs". Material truncated to the budget; token count logged. For A4 the agent starts at INDEX.md/OVERVIEW.md and may open files within budget.
  4. Grade with the grader matching gold_type; for update probes also check whether any superseded_values[] appear in the answer (supersession error); for abstention probes, UNKNOWN is the only correct answer.
  5. Aggregate. Macro accuracy over families; paired A4 − A3 differences with entity-clustered bootstrap CI; McNemar on the binary correctness; secondary: supersession error rate, abstention precision, tokens read, latency.
Validity checks
  • Gold is re-derivable two ways. Temporal and update gold is computed by two independent implementations (a Python replay of the changelog, and a SQL query over the raw JIRA export); any disagreement is investigated before the probe is kept.
  • Probes are answerable from the raw log. The retrieve-everything floor (the entity's full event history, no budget) must reach ≥ 0.9 macro accuracy; a probe it fails is reviewed and usually dropped as ill-posed.
  • Probes are not answerable from memory. A0 (model prior) must score below 0.3 on temporal/update/multi-source families; probes A0 gets right are flagged as possibly contaminated and reported separately.
  • Graders are deterministic and reproducible. Running grade_exact twice on the same outputs must give identical results; the claim grader is run twice and disagreements (< 2 % allowed) are resolved by a human.
  • Pilot with humans. 30 probes graded independently by two people and by the pipeline; pipeline-vs-human κ ≥ 0.8 required before scaling; the disagreement list is kept.
  • Leakage gate passes for 100 % of kept probes; the count of excluded probes is reported.
  • Equal budget is real. Logged token counts per arm must fall within ±10 % of 8k for all arms that fill the budget; any arm systematically under budget is noted.
E3

Store organisation — how it is run

Six stores from the identical stream; E2 probes as the yardstick at three read budgets; health measured over replay time.

  1. Build S0, S1, S4 (no LLM). S0: the fake harness writes one file per event under events/YYYY/MM/DD/. S1: a deterministic templated_store.py fills the seeded layout from structured fields (issue summary/status/assignee/components → OVERVIEW; every event → one timeline line; no synthesis). S4: embeddings over raw events, no files. Commit per window so snapshot(T) exists for each.
  2. Build S3 × 3 seeds with the real builder at 60× replay, window per D7; the builder prompt and CLAUDE.md hashed into PREREG. One additional S3 with the Opus tier (seed 1). S2 (no INDEX/topics) and S5 (S3 + embeddings over files) only if budget remains.
  3. Health checkpoints. At replay-time weeks 1, 2, 4, 8 (and end), run store_health.py on each store's snapshot and record the metrics; also run a fixed 60-probe subset at each checkpoint for the erosion curve.
  4. Run E2 against every store at budgets 2k / 8k / 32k (the read agent is the same for all).
  5. Cost accounting. Builder tokens and $ from API usage records per run, summed per store; wall time per run; files touched per run.
  6. Analyse. Accuracy-vs-budget curve per store; primary contrast S3 vs S1 and S3 vs S4 at 8k, paired per probe, clustered by entity, across seeds; between-seed variance of both accuracy and health metrics; erosion slope per store.
Validity checks
  • Same input, provably: the replay hash and the delivered-event-id list are identical across stores (diff of the builder ledger).
  • Health metrics are unit-tested on synthetic stores with planted defects (a dangling link, a duplicate fact, a superseded value left in OVERVIEW) — each must be detected.
  • S1 is a fair baseline: a human reviews 20 S1 entity folders and confirms every structured field from the events is present; if S1 is missing information available in the events, it is fixed before comparison.
  • S4 is a fair baseline: embedding model and chunking stated; recall@k of the gold source_event_ids reported so a weak retriever cannot be mistaken for a weak paradigm.
  • Seeds matter: if between-seed accuracy spread of S3 exceeds the S3 − S1 gap, the conclusion is "no reliable difference", stated as such.
  • Builder failures are counted: runs that hit the DLQ or were rolled back are reported per store; a store with > 5 % failed folds is rebuilt after the cause is fixed, and the fix is an amendment.
E4

Context envelope — how it is run

Store S3 fixed; agent fixed; only the envelope varies. Gold = what humans actually did (R) or what is correct by construction (S).

  1. Select tasks. FAST R: 150 events from the probe period that the rules floor promotes (new Blocker/Critical issue, [VOTE] thread, CVE mention) and for which the human next step exists in the log after T (assignee set, component set, duplicate link, first committer reply). S: 150 injected situations with scripted correct handling. BATCH 150 windows sampled from the probe period, each paired with the E2 probes of its entity for T = window close.
  2. Materialise envelopes V0–V8 from snapshot(T); log token counts per section. V5 additionally exposes the read tools; V6 concatenates all entity files; V7 appends superseded.md bodies; V8 shuffles sections and places state mid-prompt.
  3. Run. Fast tasks: the harness with the typed output schema (fields + drafted reply + cited IDs); 3 runs per task for pass^3. Batch windows: the builder with envelope V-x; the resulting delta is applied to a scratch copy and the entity's E2 probes are asked against it.
  4. Grade. Fast: assignee@3 / component / duplicate exact match; fact coverage of required IDs; reply quality by ROUGE-L against the human reply plus a pairwise judge in both orders. Batch: E2 accuracy of the post-delta state; evidence-citation validity (every evidence_event_ids exists and predates T).
  5. Analyse. Composite per envelope; primary contrasts V3 vs V1 and V3 vs V6, paired per task; cost per envelope; reliability pass^3; V7 vs V3 (distractor effect) and V8 vs V3 (position effect) as named secondaries.
Validity checks
  • Gold actions are human, not bot: triage fields set by known bot accounts (e.g. GitHub integration users) are excluded; the list of excluded accounts is published.
  • Gold exists after T, never before: the gate checks the human action's timestamp > T and that no envelope contains it.
  • Judge is calibrated: 200 pairwise judgements also made by two humans; κ(judge, human) ≥ 0.6 required per corpus, else reply quality is reported by ROUGE only and the judge is dropped.
  • Position bias cancelled: a win is counted only if it survives both orderings.
  • Envelopes land in their intended sizes: V3 median ≤ 12k tokens; V6 median ≥ 3 × V3; any overlap invalidates the size contrast and is fixed.
  • Task balance: per-archetype counts and per-source counts are reported; no archetype exceeds 40 % of tasks.
E5

Cadence and economics — how it is run

Same stream, same builder, same layout; only the incorporation cadence differs.

  1. Configure six cadences via the classifier settings: W1 (every event fast), W5/W20/W50 (window caps, gap and max-age scaled), W20+rules, W20+rules+deviation. W1 is run only on the last 1,000 events of the window to bound cost.
  2. Build each cadence's store (2 seeds) with usage logging on every run.
  3. Freshness. For every event, find the first commit whose diff mentions its id; delay = commit's replay-time − event time. Report p50/p95 separately for weak-label-positive events and the rest.
  4. Fidelity. Run the 300 E2 probes against each cadence's final store; run store_health.py (fragmentation: files per entity, duplicate facts).
  5. Plot cost per 1,000 events (x) against accuracy and against freshness (y), one point per cadence, with CIs.
Validity checks
  • Cost comes from provider usage records, not estimates; the exchange rate and model prices are frozen in PREREG.
  • Freshness uses the replay clock (intended timestamps), not wall-clock, so speed-up does not distort it; a pass-through calibration (events with no builder) must show ≈ 0 delay.
  • Window counts are verified: the number of builder runs per cadence must match the classifier's window-close count in its log.
  • If W20 and W1 accuracies are within CI, the claim "amortisation without loss" is supported; if W1 is significantly better, the thesis reports the price of freshness rather than hiding it.
E6

Throughput, tail latency and bursts — how it is run

Fake harness, open-loop generator on a separate machine, HdrHistogram, burst shapes from the real distributions.

  1. Fit the workload. From Corpus R (and GH Archive for volume), fit per-entity inter-arrival distributions, the entity popularity (Zipf) curve, and the burstiness B with its finite-size correction; record them.
  2. Generate shapes: steady at rates {0.25, 0.5, 1, 2, 4}× the fitted mean; benign flash crowd (volume ×5 for 10 min, type mix unchanged); anomalous burst (type-mix shift on 3 hot entities); Zipf-skewed hot entities; flash crowd + worker kill at peak. Pareto ON/OFF per entity, calibrated so the realised B matches the fitted value; also a Poisson (B → 0) control.
  3. Run each shape for two-lane (R4 router) and single-lane (everything to one topic, one builder path), with partition counts {8, 32} and worker counts {1, 4}; 25 % warm-up; ≥ 3 repetitions.
  4. Measure at the boundaries: producer→Kafka for throughput; fast-lane agent-start and batch fold-commit for latency, both against intended_send_ts; Kafka consumer lag per partition; DLQ counts; duplicates delivered.
  5. Find the knee: the highest steady rate at which p99 fast-lane latency has ~zero trend over the measurement window and lag does not grow; then run the burst shapes at 1.0× and 1.5× that knee.
  6. Guard ablation under the anomalous burst: remove the absolute floor, the multi-window confirmation, and the situation dedup one at a time; plot fast-lane admission rate and urgent-event SLO compliance on one time axis.
Validity checks
  • No coordinated omission: the generator's actual send timestamps must track the intended schedule within 1 ms at p99; if the generator itself lags, the run is invalid.
  • Calibration run: a pass-through pipeline with a fixed 10 ms sleep must report p50 ≈ 10 ms and a flat p99; this validates the clock, the histogram and the measurement points.
  • The engine is what is measured: the fake harness's service time is constant and logged; broker CPU and disk are monitored and reported so a broker bottleneck is visible rather than mistaken for the engine's.
  • B → 0 control: the two-lane advantage must shrink toward zero under Poisson load; if it does not, the "gain" is headroom, and the thesis says so.
  • Repetitions agree: p99 across the 3 repetitions within 20 %; otherwise the environment is unstable and the runs are repeated on quieter hardware.

GatesGo / no-go before spending money

G1 — after the probe pilot (wk 2): two-way gold agreement ≥ 98 %; pipeline-vs-human κ ≥ 0.8 on 30 probes; leakage gate passes 30/30; retrieve-everything ≥ 0.9; model prior ≤ 0.3 on temporal/update/multi-source. Any failure → fix generators, re-pilot. No store is built until G1 passes.

G2 — after the baseline stores (wk 4): S0, S1, S4 built from the same replay hash; S1 human review complete; S4 recall@10 of gold source events ≥ 0.7; E2 on baselines shows spread between A1 and A3 (if all baselines tie, the probes are too easy → harder families weighted up). Only then the LLM-built S3 runs.

G3 — after S3 seed 1 (wk 5): failed folds ≤ 5 %; health metrics stable (no runaway file growth); pilot E2 delta S3 − S1 has a CI that excludes zero in either direction on at least one family. Then seeds 2–3 and the Opus tier.

G4 — before E4/E5 (wk 7): OrgForge replay validated the same way as R (G1 on its probes); injected situations pass the non-triviality check in E1.

Stop rule: if at G3 the between-seed spread exceeds the S3 − S1 gap, the thesis's central result becomes "curation does not reliably beat templating at this scale", and Phase 2 prioritises E1/E6 (the two-lane contribution) over E4/E5.
