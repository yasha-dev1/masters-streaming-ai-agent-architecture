Master's thesis · evaluation design from scratch · 30 Aug 2026

How to know the context engine works

A pre-registrable protocol for a two-lane streaming context engine: six experiments, two corpora, ground truth that never depends on anyone labelling "urgent", and the answers to the questions a committee will ask.

PrinciplesFive rules every experiment below obeys

  1. Ground truth is derived, never opined. Every graded quantity is either re-derivable from the event log (a ticket's later status, a thread's actual reply, a fixing commit's files) or true by construction in a simulator. LLM judges appear only for free-text similarity, always position-swapped and κ-checked against a human sample.
  2. One variable at a time. Routing, state, organisation, envelope, cadence and system are separate experiments with separate baselines. A failure is localisable; a success is attributable.
  3. Everything is paired on a frozen replay. Every condition sees the identical event stream in the identical order; a leakage gate proves no event later than the probe time reached the store. Comparisons are paired differences with clustered standard errors, not bare means.
  4. Two corpora, for two different reasons. A real multi-source organisation for external validity; a deterministic simulated company for the sources no public data provides (clicks, payments, support for the same customers) and for injected situations with known cost of delay. A claim counts only if it holds on both.
  5. Cost is a result, not a footnote. Every quality number is reported next to tokens, dollars, and latency. The thesis argues about a trade-off, so the trade-off is what gets measured.

Dropped from the old design, deliberately: SWE-bench-Live as the primary study (the agent already has the repo, so the engine's contribution is confounded), the SPARK-only corpus, ProAgentBench, and the HBOS-vs-benchmarks study. Nothing below depends on the proposal's datasets.

DataThe two corpora

Companies receive clicks, chat, code activity, payments and tickets about the same customers and the same systems. No public dataset offers all of that for one organisation; a survey of ~60 candidates (references at the end) found the real world splits into two usable shapes.

Corpus R Real: one Apache project, three live sources

Apache Kafka (Flink or Spark as replication): the dev@ and users@ mailing lists from lists.apache.org (Pony Mail JSON/mbox, per-message epoch, sender, in-reply-to)[3], the KAFKA JIRA via public REST with changelog and comments[3], and GitHub PRs, reviews and pushes via GH Archive[12], plus the project docs site via sitemap. All open, all still live, so a post-cutoff window (e.g. 2026-01 → 2026-06) exists.

Entities: issue:KAFKA-N, pr:N, kip:N, contributor:<hash>, component:<name>. Cross-source keys (KAFKA-NNNN, KIP-NNN) are mandated in subjects and commit messages, so joins are deterministic.

Gives: chat-like discussion (email threads), issue state machine, code activity, docs. Lacks: customers, clicks, payments. That is what Corpus S is for.

Alternative with true chat texture: Lean or Rust Zulip archives (web-public, per-message timestamps, PR cross-references) + GitHub[1][2]. Use as a replication if time allows.

Corpus S Simulated company with ground truth by construction

OrgForge (MIT, arXiv 2603.14997, Mar 2026): a deterministic Python engine owns every fact; an LLM writes only prose. It emits an append-only, ISO-timestamped event bus generating Slack channels and DMs, Jira tickets, GitHub PRs and reviews, Confluence pages, Zendesk tickets, Salesforce records, invoices, NPS, and Datadog metrics/alerts, every artifact traceable to a SimEvent[15].

Extend it with the two sources it lacks: a REES46-shaped clickstream generator (view / cart / purchase per customer and session, with real distributions fitted from the 285 M-event REES46 data)[7], and Stripe events from the Stripe sandbox using test clocks and dispute fixtures (charge.dispute.created/updated/closed, refunds, failed invoices)[9].

Gives: every source a company sees, about the same customers and systems; a world state queryable at any T; injected situations (dispute on a VIP, incident, churn signal, on-call page) with known onset times and assigned cost-of-delay; arbitrary scale for load tests.

Honesty: a single-author preprint; ~150 artifacts per 22-day run by default and must be scaled; prose quality depends on the generator model. Every result must replicate on Corpus R to count.

Why not one of the other 58

Kubernetes/CNCF Slack history is no longer accessible (free-tier retention since June 2025); Linen.dev mirrors have no bulk API; Public Jira Dataset (32 M changelog entries, CC BY) is excellent but frozen at Jan 2022 and single-source — used here only for label-noise calibration; Retailrocket / OTTO / Olist / Customer-Support-on-Twitter are single-company single-source and pre-2023 — used to fit generator distributions and as sanity corpora, not as the main stream; TheAgentCompany offers real GitLab/RocketChat services but no event log; Gaia2/ARE are consumer apps, not a company. Full survey in the references.

Leakage gate (applies to every experiment)

Before any probe at time T, assert that no event with time > T was ever delivered to the builder before the snapshot used, and that the probe question contains no post-T tokens. Log the assertion per probe; report the count.

E1

Routing under a budget

Does the router put high-cost-of-delay events in the fast lane better than equally budgeted baselines — and is promoting them actually useful?

Variable
Router policy, at fixed admission budgets b ∈ {1 %, 2 %, 5 %, 10 %}.
Conditions
R0 random-at-budget · R1 rules-only · R2 global z-score (no entity keying) · R3 per-entity robust-z without guards · R4 rules + per-entity robust-z + absolute floor + multi-window (ours) · R5 always-fast (cost ceiling).
Ground truth
S: injected situations with hard negatives. R: weakly-supervised labels; report label-model accuracy and agreement between sources.
Primary metric
recall@budget of high-cost events at b = 2 %, per source. Secondary: precision@budget, VUS-PR (threshold-free), affiliation precision/recall (lateness per situation), median and p95 detection delay, NAB score under the low-FN profile. No point-adjusted F1.
Harm check
For events R4 promotes, run the fast-lane agent now and again at window close; compare action quality (E4 grader). If equal, promotion bought nothing — report it.
Robustness
Jitter injected onset times ±5 min; flip 10 % of weak labels; rankings must be stable. Sweep θ per source and report the operating curve.
Sample
S: ≥ 200 injected situations across ≥ 4 archetypes × 3 seeds. R: one 6-month window, ≥ 30 k events, ≥ 300 weak-positive events.
Cost
No LLM needed except the harm check (~2 × 200 short runs).
E2

State fidelity

After replaying the stream, is the per-entity state correct and current?

Variable
What is read to answer a probe (store vs. raw alternatives), with the same read agent and read budget.
Conditions
A0 nothing (model prior) · A1 raw last-N events of the entity (N = 20, 100) · A2 BM25 top-k over raw events · A3 embedding top-k over raw events · A4 curated store (read agent starts at INDEX/OVERVIEW) · sanity floors: retrieve-everything, retrieve-nothing.
Probe families
  • Extraction — "what is the current plan / component / owner of X?"
  • Temporal — "what was the status of X as of T?" (T sampled inside the window)
  • Knowledge update — facts that changed at least twice; answer must be the latest, and the store must not return the superseded value
  • Multi-source — "which PR / thread / ticket relates to X?"
  • Abstention — facts that do not exist; answer must be "unknown"
Grading
Exact match after normalisation for fields and IDs; claim-level context precision / recall for free-text facts (gold decomposed into atomic claims); link recall / precision for cross-source probes.
Primary metric
Macro accuracy over the five families for A4 vs A3. Secondary: supersession error rate, abstention precision, tokens read per probe, tool calls per probe, latency per probe.
Sample
≥ 300 probes per corpus, stratified across families and entities; ≥ 150 entities.
Cost
~300 × 5 arms × 2 corpora short read-agent runs per seed.

Primary metric
E2 macro accuracy at the 8k read budget, S3 vs S1 and S3 vs S4. If S1 ties S3, the LLM curation is not earning its cost — that is a publishable finding.
Sample
Both corpora; 3 seeds for LLM-built stores (S2, S3, S5) since the builder is nondeterministic; report between-seed variance of the store itself.
Cost
The expensive experiment: 3 LLM-built stores × 2 corpora × 3 seeds ≈ 18 full replays. Cap replays at ~4k events each; use a mid-tier model for the sweep and the frontier model for S3 only, stated per arm.

E5

Cadence and economics

The fast/batch split as a knob: how does the granularity of incorporation trade cost, freshness and fidelity?

Variable
Incorporation cadence on the same stream, store S3.
Conditions
W1 one event per run (everything fast) · W5, W20, W50 session windows with those caps · W20+rules (ours: window 20, rules floor promotes to fast) · W20+rules+deviation (ours, full).
Metrics
Cost: builder tokens and $ per 1,000 events, agent runs per 1,000 events. Freshness: event → reflected-in-snapshot delay, p50/p95, separately for high-cost and routine events. Fidelity: E2 macro accuracy of the resulting store; fragmentation (duplicate facts, files per entity). Curve: fidelity and freshness against cost, one point per condition.
Primary metric
Cost per 1,000 events at equal E2 accuracy (within CI), W20+rules vs W1. The claim is that the batch lane amortises without losing fidelity; the fast lane buys freshness only for the budgeted events.
Sample
Both corpora; 2 seeds (cost-limited). W1 capped to the last 1,000 events of the window.
E6

Throughput, tail latency and bursts

With the LLM mocked, does the pipeline sustain load, protect the fast lane during bursts, and avoid amplifying them?

Method
Open-loop replay from separate hardware at fixed rates; latency measured from the intended send time (coordinated-omission-safe); 25 % warm-up; sustainable throughput = the knee where p99 event-time latency stops being flat; resource demand = the minimal partitions/workers meeting the SLO at each load, swept over event rate and entity cardinality. Harness = fake (deterministic, ~constant service time), so the measurement is of routing, windowing and store commits, not of an LLM provider.
Workloads
From Corpus S at matched burstiness B (fit on Corpus R and on REES46/GH Archive): steady · benign flash crowd (volume ×5, mix stable) · anomalous burst (type-mix shift on a hot entity) · Zipf-skewed hot entities · flash crowd + mid-burst worker kill.
Metrics
Fast-lane latency to agent-start p50/p99/p99.9 during the burst window; batch-lane fold latency and staleness; consumer lag spike height and drain time; recovery time after kill; per-partition lag Gini; fast-lane admission rate over time plotted on the same axis as urgent-event SLO compliance (the self-amplification chart); cross-entity fairness (do cold entities' urgent events still make SLO during a hot-entity burst?).
Ablations
Two-lane vs single undifferentiated lane; guard ablation — remove the absolute floor, the multi-window confirmation, and the per-window situation dedup one at a time; B → 0 (Poisson) control, where the two-lane advantage must shrink toward zero.
Primary metric
Fast-lane p99.9 SLO attainment for injected urgent events at 1.5× the single-lane knee, two-lane vs single-lane, and its gap as a function of B.
Cost
No LLM. Compute only.

RigorProtocol and statistics

Pre-registration

Before running anything, commit a document to the repo fixing: the corpus windows and seeds; each experiment's conditions, primary metric and the comparison it tests; the budget values, θ per source, window caps; the model per arm (builder, read agent, judge — judge from a different family); the exclusion rules; and the analysis code. Deviations are logged as amendments with dates. This is what lets you say "we did not shop for metrics."

Statistics

  • All comparisons are paired per probe / task / situation on the identical stream; report the paired difference with a BCa bootstrap 95 % CI (10,000 resamples). Probes sharing an entity are not independent: cluster by entity.
  • Binary outcomes between two conditions: McNemar's test on the discordant cells.
  • One primary metric per experiment, named above; Holm–Bonferroni across the secondaries of that experiment.
  • Power: to detect a 10-point difference in a proportion near 0.6 with paired data, α = 0.05, power 0.8, n ≈ 150 paired units — the sample sizes above are set from this.
  • Nondeterminism: ≥ 3 seeds for every LLM-built store; report pass^3 for tasks and the between-seed variance of probe accuracy and store-health metrics. Temperature 0 does not remove it; say so.
  • Sanity floors always run through the same code: random router, retrieve-everything, retrieve-nothing, model-prior. Any metric that ranks a floor near the real system is broken for this setting and is dropped.

Human audit

Derived ground truth can be wrong (a JIRA field set late, a simulator prose error). Sample 200 probes and 100 gold actions across both corpora; two annotators check gold correctness and grade a subset of free-text outputs; report Cohen's κ for annotator agreement and for judge-vs-human. Trust judge scores only on slices where κ ≥ 0.6.

Reproducibility package

Frozen replay files (event JSONL with intended timestamps), corpus builders (Pony Mail / JIRA / GH Archive extractors; OrgForge config and seeds; Stripe fixture scripts), prompts and schema versions, probe sets with gold, analysis notebooks, and the exact model IDs and dates. A reader should be able to re-run E2 on S0 vs S3 in an afternoon.

DefenseThe questions they will ask

01You never labelled what "urgent" means. How can you evaluate routing?

Because "urgent" as a human label is unreliable: about half of duplicate bug reports carry inconsistent severities, and a third of "bugs" are misclassified. We define the fast lane operationally as high expected cost of delay, then evaluate against two things that do not need that label: injected situations with known onset and cost in the simulator, and weakly-supervised outcome labels on the real corpus (resolved within 24 h, committer reply within 1 h) whose noise is modelled. We also check whether promotion changed the outcome (E1 harm check). Ranking quality without a harm check is not enough — a 0.94-AUROC trigger has been shown to hurt.

02Isn't the simulator a toy?

It is the only way to get clicks, payments, chat and tickets about the same customers with a queryable world state; no public corpus has that. It is used for what real data cannot provide — exact state at T, injected situations, arbitrary load — and every claim must replicate on the real Apache corpus to count. Distributions are fitted from real click and payment data and burstiness is matched to real streams.

03Isn't this just RAG with extra steps?

E3 tests exactly that: S4 is a vector index over raw events with the same read agent and read budget. The difference between RAG and a maintained store is accumulation — RAG re-retrieves from a static log and rediscovers state every time; the store folds. If S4 ties S3, we say so. S5 tests whether both together are better.

04Why should an LLM organise files? A rule-based Customer-360 does this already.

That is S1, built by code with no LLM, and it is a required baseline. The thesis's claim is only defensible if S3 beats S1 per token on the multi-source and knowledge-update probe families, where fixed schemas cannot know in advance what matters. If S1 ties, the finding is that curation is not worth its cost for this data — still a result.

05Your builder is nondeterministic. How is any of this reproducible?

The replay is frozen, prompts and schemas are versioned, gold is deterministic, and every LLM-built store is built three times with different seeds. We report between-seed variance of both probe accuracy and the store's own shape, and pass^3 for tasks. Nondeterminism is a measured property of the system, not an excuse.

06The model has read Kafka's entire history. Isn't it answering from memory?

Windows are post-cutoff for the real corpus; the A0/V0 arms measure what the model knows with no store; and gold facts are later events (a status transition, a reply), not encyclopaedic facts. For the simulator, contamination is impossible by construction.

07How do you know the state is right if no human checked it?

Because "right" is defined against facts re-derived from the log or the simulator, not against opinion. We additionally audit 200 probes and 100 gold actions with two annotators and report κ, so the reader can see how often derived gold is itself wrong.

08Why two lanes? Why not process everything immediately, or everything in batches?

Both are arms. W1 (everything fast) shows the cost ceiling; W50 shows the freshness floor; E6 shows the single lane's urgent tail collapsing under burst while the two-lane holds it, and that the advantage shrinks toward zero as burstiness goes to zero — proving the gain is burst-specific, not free headroom.

09Isn't the 2 % budget arbitrary?

It is a parameter and it is swept (1, 2, 5, 10 %). The claim is about the shape of the operating curve, and the budget is the operator's knob; we show what each setting buys.

10What is "the best context"? Best for what?

Operationally: the envelope that maximises action quality against human/gold actions per token. E4 holds the agent, the store and the task fixed and varies only the envelope, including a "stuff everything" ceiling and a distractor arm. "Best" is whichever arm wins that paired comparison at a stated token budget, and we show the whole curve.

11Does the organisation hold up, or does the store rot?

Measured directly: store-health metrics and probe accuracy at weeks 1, 2, 4 and 8 of replay. Prior work found filesystem-memory organisation erodes for all but the strongest management agents; we report our erosion curve rather than a single end-of-run number.

12What does it cost?

Every quality number is reported next to tokens, dollars and latency, and E5 gives cost per 1,000 events per cadence. Cost is a result of the thesis, not an appendix.

13You run a single node. Where is the scalability?

E6 reports resource demand as a function of load and entity cardinality (the Theodolite method) because per-entity state shards on the same key the stream partitions on. We show the demand curve on one node and argue linearity from the keying, and we say explicitly that multi-node is future work.

14Your latency numbers exclude the LLM. Isn't that hiding the real bottleneck?

Deliberately. E6 measures the engine — routing, windowing, commits — with a deterministic harness so the number is not a measurement of a vendor's API. The LLM cost is reported separately as agent-runs and tokens per 1,000 events per lane (E5), which is the quantity a deployer can act on.

15How is this different from Confluent's Real-Time Context Engine or Flink Agents?

They materialise per-entity state with SQL views defined by a developer and trigger agents on developer-written conditions. Here an agent harness folds heterogeneous events into human-readable state, a label-free budgeted lane decides what is urgent, and the state's fidelity is evaluated against derivable ground truth. Each piece has a neighbour; the intersection does not exist, and neither does the evaluation.

16Why markdown files rather than a graph or a database?

Inspectability (a human can read and diff the state), versioning for free, and tool-native access for coding-agent harnesses. The graph alternative is represented by the vector arm and by the templated store; if a structured store wins per token, the thesis reports it. Evidence exists both ways — a filesystem agent beat a graph memory on LoCoMo, and a 2026 study found file organisation erodes — which is why E3 exists.

17Email is not Slack. Clicks from 2019 are not today's. Is the data realistic?

The real corpus is real, live and multi-source; it lacks customers. The simulator supplies customers, clicks and payments with distributions fitted from real data. We state the nature of each source and, where the thesis needs a chat texture, use Zulip archives as replication. No claim rests on one corpus.

18What if the curated store loses?

Then the thesis reports that a templated or retrieval-based store is sufficient at this scale, with the cost curve to prove it, and the two-lane and evaluation contributions stand on their own. The protocol is pre-registered precisely so that a negative result is credible.

19Ethics and licences?

Apache lists, JIRA and GitHub are public under ASF and GitHub terms; contributor identities are hashed; nothing is redistributed beyond IDs and derived probes. The simulator is MIT and contains no real people. Reused datasets (REES46, Olist, Retailrocket) are used only to fit distributions, within their licences.

20Which single result should we look at?

The E3 curve: probe accuracy against read budget for S1, S3 and S4 on both corpora, with the erosion checkpoints. It answers whether organising the store is worth it, per token, over time. Everything else explains why and what it costs.
