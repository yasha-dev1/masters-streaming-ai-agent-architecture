Read this first: three decisions that unblock the draft

The evaluation feels impossible because the repo contains three evaluation designs that disagree with each other and none of them matches the implementation. research/evaluation-methodology.md pre-registers seven hypotheses and eleven experiments (VUS-PR, Theodolite demand curves, ContextBench, LongMemEval, push-vs-poll Pareto) on a Flink + Paimon + bitemporal-graph stack that does not exist. proposal.md replaces that with Study 1–3 (SWE-bench-Live, anomaly benchmarks, Apache JIRA) but still lists ProAgentBench as Deliverable 5. research/are-time-aware-evaluation.md then re-operationalises Study 3 as an order-discrepancy score. Nothing is wrong with any single document; the problem is that you have not yet chosen. Choose:

1

Make the builder the thesis, not the classifier.

The proposal already says "this MCP tool is the thesis deliverable" and the README says "the novel component is the builder". The classifier as implemented is a Welford z-score on inter-arrival gap with a rules stub. Reframe the fast/batch split as an incorporation-cadence knob of the builder (how often the agent folds events into the store), and demote HBOS/anomaly routing to a design discussion plus, at most, one offline notebook experiment.

2

Run one primary study on the SPARK corpus you already have, with deterministic probes.

You have 10,659 fixed SPARK bugs, 46,902 commits, an 89.7 % ticket↔commit join with 99.7 % temporal validity. Replay a window through harnext, then ask the MCP context_research tool questions whose answers are known from the data itself: which files, which commits, what status as of when. No JVM build, no test harness, no LLM judge for the headline metric. Details in Evaluation you can run.

3

Write the proposal down to what shipped, and name the rest future work.

Fork-per-session + optimistic commit, the internal filesystem MCP server, Flink keyed state, Paimon archive, the bitemporal graph + RAG store, the Kafka delivery contract and Python SDK: none of these exist, and a committee will find that in ten minutes with the README. Single-writer-per-org with linear snapshots is a perfectly defensible v1 consistency model — say so, and state its guarantees formally (that alone answers RQ5 open question 1 in your own notes).

The proposal on one page

Problem
Agents over high-volume heterogeneous event streams (Slack, JIRA, telemetry) need the right context at the right time, with urgent events surfaced immediately; no open-source reference architecture exists. Confluent's Real-Time Context Engine is the closed-source, pull-only prior art.
Commitment A
The CMS builds context from the stream using stateless builder agents. All long-lived state is a per-org versioned filesystem (AgentFS, SQLite) plus a raw-conversation log. Kafka and the filesystem never cross the CMS boundary.
Commitment B
The only external surface is MCP: context_research (synthesized, cited answer), context_get_urls, context_update (spawns an internal write agent). "Context is a service the CMS synthesizes on request, not a store the caller browses."
Routing
Each event goes FAST (processed on arrival) or BATCH (window's events at window close). Decision = rules floor OR per-entity HBOS anomaly score past a static per-source threshold, guarded by an absolute-volume floor and multi-window confirmation. No online feedback loop.
Envelope
CloudEvents 1.0; subject (customer:42, repo:apache/spark) doubles as Kafka partition key and anomaly-state key.
Delivery
Section "Delivery surface" commits to Kafka-direct (event, context) envelopes on cms.events.{fast,batch}.v1 with consumer groups per agent role and a Python SDK. This section predates Commitment B and contradicts it — see below.
Evaluation
Study 1: SWE-bench-Live with the CMS as the agent's only memory, % resolved vs. no-memory and full-dump ablations. Study 2: HBOS + per-entity normalisation vs. global HBOS and streaming-AD baselines on NAB/TSB-AD and the Public Jira dataset. Study 3: live Apache JIRA + Git + PR streams (SPARK), context precision/recall against the fixing commit's files.
Deliverables
Thesis report; Kafka delivery contract; reference implementation (Redpanda + Flink + Paimon + bitemporal graph + RAG store); Python SDK; ProAgentBench evaluation.

What is missing for a first draft

In the proposal

  • Related work. Nothing on agent memory systems (MemGPT/Letta, Mem0, Zep/Graphiti, A-MEM, LangMem), on "context engineering", or on file-based agent memory. The research notes cover streaming and anomaly detection well; the memory side is only in RQ5.
  • A definition of "context". The old design had a per-event context object; the FS design has files. What is a Context Unit now? (Suggested: a snapshot-consistent answer synthesised from the FS as of snapshot s.)
  • Consistency model statement. What does a reader of context_research see relative to concurrent builds? (Snapshot isolation, monotonic snapshots, single writer per org — all true today, none written down.)
  • Threats to validity, cost budget, data licensing (Apache JIRA/GitHub content is public; SWE-bench-Live is MIT), timeline.
  • One chosen evaluation (see next section).

In the implementation

  • Replay tooling. A script that turns eval-prototype/data/*.jsonl (+ ticket changelogs and comments) into CloudEvents in recorded order with a cutoff gate, producing to cms.events.raw.v1. The GitHub connector already shapes commit/issue events; reuse its types.
  • JIRA event type. There is no com.atlassian.jira.* connector; add a minimal one (issue created, changelog transition, comment).
  • Rules floor. Two lines: priority ∈ {Blocker, Critical} → FAST. This is enough for the cadence experiment.
  • Probe runner + metrics. Calls context_research per held-out ticket, parses cited paths/keys, scores against gold, writes a CSV. ~200 lines.
  • Baseline retrievers that answer the same probes without the builder: BM25 over raw events; embeddings over raw events; the fake harness (dump, no curation).
  • Cost/latency instrumentation per build and per MCP call (usage is already returned by the harness; persist it).

Where the novelty is (ranked by defensibility ÷ effort)

Everything below is testable with the SPARK corpus and the current builder. The classifier and the fork model are deliberately not on this list.

1

Agent-as-curator: a coding agent, not a pipeline, decides how knowledge is organised and superseded

Every surveyed memory system (Mem0, Zep, MemGPT, GraphRAG-style summaries) uses a fixed extraction schema — entities, triples, summaries — chosen by the system designer. Harnext gives a general coding agent a filesystem, a CLAUDE.md contract and an event, and lets it choose files, sections and supersession. The claim to test: agent-curated files beat retrieval over the raw event log on questions that require synthesis across events, at bounded token cost. The fake harness (append, no curation) and a BM25/embedding retriever over raw events are the two ablations and both are nearly free.

2

Incorporation cadence: the fast/batch split as a cost–freshness–quality knob of the curator

Nobody has measured how the granularity of updates to an agent-maintained store affects its quality. One event per agent run (FAST) is fresh but expensive and prone to fragmentation; twenty events per run (BATCH) is cheap and lets the agent dedupe, but stale. Sweep window size {1, 5, 20, 50} on the same replayed stream and report retrieval quality, builder tokens per event, and staleness (event time → time reflected in a snapshot). Adding a priority rule (Blocker → FAST) gives the mixed condition. This reuses the lane machinery you built and turns RQ2 into something measurable without HBOS.

3

Supersession correctness under streaming updates

JIRA changelogs give exact ground truth for "what was the status / assignee / fixVersion of SPARK-N as of T". A store that appends but never supersedes answers wrong; a curator that rewrites OVERVIEW.md and logs _meta/superseded.md should answer right. This is the file-system version of the bitemporal question in RQ5, and it is deterministic to grade. It also directly exercises the prompt's "never rewrite timeline, keep OVERVIEW current" contract.

4

Cross-source linkage emerges from curation

The regex join ([SPARK-NNNNN] in commit messages) is the gold for "which commits fixed this ticket". Does the curated FS link ticket ↔ commit ↔ PR files without being told to join? Measure link recall in the store versus the gold join. This is the proposal's Study 3 question ("cross-source context an agent could not get from any single feed") made concrete.

5

A stated consistency model for a single-writer snapshot store (small, theoretical)

Readers get snapshot isolation on an immutable snapshot; snapshots are linear per org; writes serialise per org; context_update is a write through the same agent. Write it as four guarantees with a short argument each. RQ5 open question 1 in your notes calls this "a concrete thesis contribution opportunity". It costs a page.

What to say about the classifier. Keep the per-entity anomaly-detection design as a chapter section with the Cloudflare framing and the rules-floor argument — it is good design writing. State the implementation as rules + per-entity z-score, and if time allows run one offline notebook (pyod HBOS vs. global HBOS on the Public Jira priority labels, recall@FPR ≤ 1 %) as a secondary result. Do not let it be the thing the committee judges.

Evaluation you can run

Does an agent-curated context store, updated from a replayed event stream, serve better context than retrieval over the raw stream — and how does update cadence change cost, freshness and quality?

Optional headline: Study 1, small

If budget allows after P1–P5: 20–30 SWE-bench-Live instances from one or two Python repos, arms agent + repo vs. agent + repo + CMS over MCP, % resolved plus tokens. Treat it as an existence proof that the store can be a coding agent's memory, not as the primary result — the deltas will be small because the agent already has the repo.

Statistics

  • Everything is paired per ticket. Report the paired difference with a BCa bootstrap 95 % CI (10k resamples); McNemar for binary hit@1 and P2 exact match.
  • Pre-register the primary metric: P1 file-level recall@10 for C4 vs. C2. Everything else is secondary; apply Holm–Bonferroni across the secondary set.
  • Non-determinism: the builder is an LLM. Run the C4 build with ≥ 3 seeds (or 3 independent replays) and report between-run variance of the store (file count, P1 score) — this is itself a finding about agent-curated stores.
  • Sanity floors: C0 must lose; a "retrieve everything" arm must have recall → 1 and precision → prevalence.

Threats to validity to write down now

  • Construct: file localization is a proxy for "right context"; P2/P3 mitigate by testing different needs.
  • Contamination: the model may know SPARK's code; the window post-dates most training cutoffs, and C0 measures what the model knows without any store.
  • Single repo: SPARK only. Add Flink or Kafka for a second corpus if time remains; otherwise say so.
  • Join noise: 10 % of fixed bugs have no linking commit; they are excluded, which biases toward well-documented fixes.
  • Builder stochasticity: covered by seeds above.

Draft outline, research questions, contributions

Research questions (rewritten to match what will be measured)

  1. RQ1 — Curation. Can a stateless coding agent maintain a coherent, per-organisation context store from a heterogeneous event stream, and does the curated store serve better context than retrieval over the raw log at comparable token cost? (P1, P3, P5)
  2. RQ2 — Cadence. How does the granularity of incorporation (per event vs. per window, with a rules-based fast lane) trade freshness, cost and quality? (P4, P5, P1 across C4-w)
  3. RQ3 — Consistency. What temporal-consistency guarantees does a single-writer, snapshot-versioned filesystem give its readers, and does the curator honour supersession in practice? (formal statement + P2)
  4. RQ4 — Interface. Is a synthesis-only MCP surface (no store browsing) sufficient for an external coding agent? (Study 1 small, plus P6)

Contributions to claim

  1. An open-source reference architecture for a streaming context engine whose store is an agent-curated versioned filesystem, exposed only through MCP.
  2. The first controlled measurement of agent-curated versus raw-log retrieval, and of incorporation cadence, on a real multi-source software-engineering stream.
  3. A replayable evaluation corpus and probe suite (SPARK JIRA + Git + PRs, gold from the ticket–commit join) with a leakage gate.
  4. A stated consistency model for single-writer snapshot stores and an empirical supersession test.

Related work to cite (the memory side is the gap)

The streaming, anomaly-detection and benchmarking literature is already well covered in research/. These fill the memory/context-engineering half. Verify each before citing; arXiv IDs from memory should be checked.

  • Agent memory systems: MemGPT / Letta (Packer et al., 2023); Mem0 (Chhikara et al., 2025); Zep / Graphiti temporal knowledge graph (Rasmussen et al., 2025); A-MEM (Xu et al., 2025); Generative Agents reflection memory (Park et al., 2023); LangMem; Cognee.
