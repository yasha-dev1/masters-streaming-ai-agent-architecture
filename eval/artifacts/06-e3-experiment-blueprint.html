01 / PURPOSE

Choose a strategy, and explain why it works.

System comparison

Which complete configuration answers the most questions correctly under a fixed read allowance, while meeting freshness and reliability constraints at the lowest lifecycle cost?

The unit is a configured engine: representation + writing policy + builder + retrieval + reader.

Mechanism comparison

Does an index help? Does a fact ledger prevent stale answers? Do shell tools change the benefit of a template? These require controlled differences and crossed factors.

The unit is a paired change: one factor, or one explicitly modeled interaction.

“Optimal” means best supported within the tested configurations and declared workload.

We will report a quality–freshness–cost frontier and recommend a default for a stated query volume. We cannot establish a universal optimum over all prompts, graph schemas, models, or future workloads.

Frozen streamIdentical observable events and initial state
Independent buildsEach configuration and replicate owns its store
Historical snapshotsNo future records, indices, or Git history
Budgeted readerStructured answers and complete tool traces
Frozen gradersFacts, links, costs, uncertainty, decisions

The thesis claims covered: C2, correct maintained state; C3, useful organization and read efficiency over stream growth. E4 still tests action quality; E5 tests operational cadence and freshness; E6 tests live throughput, latency, recovery, and concurrency. E3 includes controlled schedule and robustness diagnostics, not a substitute for those experiments.

Three query pools, with different purposes

DEVELOPMENT

160 Kafka probes + controlled cases

Four UTC scoring blocks: Jan 24–25, Feb 21–22, Mar 21–22, Apr 18–19. Each has seven preceding days of warm-up. Forty questions per block, eight per primary family.

If a block lacks gold support, enlarge backward within Jan–Apr by a recorded rule before any model scoring. Never borrow May–June questions. Short windows screen mechanisms; they cannot evidence six-month sustainability.

SELECTION

300 May–June probes

60 per family. Group by connected issue/PR/thread component before assignment; balance week, source, history length, and transition count where feasible.

Prompts and candidate configurations freeze before this stage. Use the set to select finalists under the registered rule, not to rewrite templates repeatedly.

CONFIRMATION

300 sealed probes initially

Same family allocation; disjoint related-entity groups from selection where support permits. Hash and withhold the questions and gold from tuning and builders.

300 is a starting design. Development-only power simulation may increase the count before sealing. If the corpus cannot support grouping or precision, narrow the claim or add data; do not duplicate probes to meet a quota.

Development entity exposure is logged. Builders legitimately see all permitted stream entities; the split prevents query/gold-driven tuning on final test groups. Add a confirmation stratum of entities unseen in development where possible. This is within-project evaluation, not proof of transfer to unseen organizations.

Controlled stream: 240 probes for mechanisms that the real corpus cannot label reliably

Use six constructed mechanisms with 40 probes each: repeated updates; delayed corrections; duplicate delivery; explicit versus ambiguous aliases; contradictions with recorded authority; missing then newly available facts. Gold is generated from a separate state machine. Give all arms identical records and emit paired unperturbed/perturbed streams. Report these scores separately from Kafka macro accuracy; do not mix synthetic wins into the primary.

Arrival variants: no added delay, 1 hour, 24 hours. Duplicate variants: 0% and 10% event re-delivery. Correction variants preserve event identity and issue a new content version. Alias cases include both genuine aliases and similarly named distinct entities, so merging everything fails. The 240-probe audit is a baseline set; variants are paired repeated conditions, not independent additional subjects.

04 / MEASUREMENT

Deterministic grades over stochastic agents.

The model may produce a different store or answer on another run. Given an archived answer, gold record, and grader version, the grade must be identical. We test factual retrieval and maintenance; unrestricted prose quality is outside the primary deterministic score.

Reader output contract

{
  "probe_id": "q-0042",
  "status": "answered",
  "values": ["user:bob"],
  "evidence_ids": ["jira:change-127"],
  "files": [],
  "relations": []
}

Gold and expected values are held by the evaluator only. Typed fields avoid grading “Bob” differently from “The owner is Bob.” Per-probe schemas declare scalar versus set, accepted canonical aliases, and expected null behavior.

Gold derivation contract

Replay JIRA changelog state independently in Python and SQL over raw source records. Use explicit PR/issue keys and file metadata for relation/file gold. Check agreement on all proposed eligible cases before removing disagreements.

Human-audit 30 balanced development probes, including question interpretation and allowed evidence. Require ≥98% dual-gold agreement where applicable and ≥0.8 annotator agreement κ; publish denominators and confidence intervals. A shared upstream extraction bug can fool both implementations, so audit raw records too.

Diagnose the pipeline.

Record whether the necessary structured fact survives construction, whether required evidence reaches the reader, and whether the reader answers correctly given that evidence. Prose-store fact presence is not always deterministically decidable: use an oracle-evidence reader condition and a human-audited error sample instead of treating keyword presence as semantic proof.

Qualitative error review uses 50 stratified errors per finalist, blinded to configuration where possible, with fixed categories and disagreements recorded. It explains mechanisms; it does not replace the primary score or tune on the sealed set.

P0: preserve every supported atomic fact and explicit relationship in the allowed records; remove exact redundancy; concise wording is allowed but factual omission is not. P1: prioritize current state, decisions, dependencies, blockers, and supported historical transitions; compress conversational repetition and incidental prose. Both preserve all evaluated structured state fields, all changes to those fields, and their evidence. Thus P1 tests narrative selectivity, not permission to drop correctness-critical fields.

T0: list/read/search/write/edit tools with bounded returns. T1: shell operations confined to the identical store and source directory, no network and no additional utility containing hidden data. Tool permission and prompt instructions must agree. Translate the same contract into each harness’s instruction mechanism; do not let a Claude-only instruction file disappear in another adapter.

Format choices, enforcement, and the “pretty folders” trap

Default file granularity is atomic fact sections split above 200 tokens, page cap 2k tokens, shared title/entity/source frontmatter. File-size study D05 varies section threshold and page cap independently; overflowing sections split with stable IDs. The 200-line legacy cap is recorded as a legacy condition only: line length makes it an imprecise size control.

Validate only the commitments each condition actually makes. F4 cannot fail for lacking INDEX; F6 cannot fail for choosing a different taxonomy. All stores must preserve scope, parseable provenance, and valid paths. A broken index, dangling link, or oversized page is a measured defect. Correctness is decided by probes; no score is awarded simply because the directory tree resembles the desired layout.

F6 and F2 are extension challengers, not variations silently substituted into the 12-cell matrix. F2 keeps source bytes unchanged and only moves files; its test at matched checkpoints isolates taxonomy. Its native weekly cadence is a separate service variant. F3 preserves content while periodically rewriting raw staging into organized files; it belongs to D07, not an unqualified structure-only contrast.

Prediction: lexical/hybrid retrieval should be strong on explicit issue IDs; dense retrieval may help paraphrases. Entity bundles may recover dispersed evidence but waste tokens on unrelated state. Reranking may improve evidence recall but fail to repay its latency. All four are hypotheses, not assumed improvements.

Gold-source recall is reported against acceptable minimal evidence sets, not merely the first source ID listed by the generator. If any one of several events establishes a fact, retrieving one valid set is sufficient. If multi-hop evidence needs two records, both are required. This prevents a redundant archival copy from creating an artificial retrieval failure.

08 / KNOWLEDGE-GRAPH REGIME

Separate the graph schema from its extraction and resolution.

The core graph screen is 2 schemas × 2 extraction policies × 2 identity-resolution strategies = 8 configurations, all built with M0 on the same W60 stream. Use one reference temporal edge-table implementation to isolate the representation/extraction choices. It is a research comparator, not a claim that this backend is production-optimal.

G0 · Generic attributed edges

Entities plus source-backed relations with free-text relation labels, descriptions, and immutable episode provenance. A fixed evaluator-side adapter maps unambiguous known predicate aliases; ambiguous mappings are not silently granted credit.

Prediction: broader coverage but more duplicate predicates and noisier neighborhoods.

G1 · Typed assertions

Entities: issue, person, PR, thread, file, version. Predicates include assigned_to, has_status, targets_version, references_issue, changes_file, discussed_in. Additional domain predicates are frozen on development.

Prediction: cleaner exact state and relationship queries; possible missed relations outside the vocabulary.

This is a proposed cap, not a usage forecast. If a provider exposes separate reasoning tokens, count them in output/compute accounting. Same tools may create different billed context across harnesses; report it, rather than force fake token equality.

Replicates: new independent store from the same causal initialization, same prompt, same model, same settings. Run IDs are not inserted into the builder prompt. The existing “evaluation seed” text is a prompt perturbation, not a provider seed. If no sampling seed is supported, record that and repeat invocations; temperature zero alone does not justify a reproducibility claim.

Do not eliminate a representation after one unfavorable builder combination.

Keep at least one file, graph, and retrieval contender through development. Run the M0/M1 interaction block before family selection. Preserve any configuration with a credible quality/cost advantage or a unique temporal/multi-source benefit. Every retention decision is recorded; full claims are still conditional on the finite set of configurations tested.

10 / EXECUTION DESIGN

Screen widely on development. Confirm narrowly on the full stream.

S0 · Validate the experimental instrument

Freeze causal input fields and initialization; independently derive gold; validate snapshots, typed answers, provider adapters, usage, and planted failures. Count candidate schedules. No full LLM store builds. Deliver the manifest and the two-human pilot before scaling.

S1 · Establish controls and cost

Build F0, F1, F1-L and retrieval infrastructure on development. Run closed-book and oracle-evidence controls. Pilot F5 on early, middle, and late development blocks. Measure usage and failures; bind model roles and a total dollar/wall ceiling. The paper-quality gate is answerability, not whether baselines differ.

S2 · Crossed development screens

S-F: 12 file configurations; S-R: 12 retrieval configurations; S-G: 8 graph configurations. One build per learned cell per development block; a result is a mechanism screen, not stable full-stream evidence. Run Q0 at 8k on all 160 development probes.

S3 · Targeted development studies

Builder models first, then reader strength/tools, retrieval/graph query settings, file size, embedding model, harness, build allowance, and optional challengers in the declared priority order. Freeze final prompts/settings and candidate membership before May–June selection scoring.

S4 · Full-stream selection

Run the six-month primary schedule for up to three file, two graph, and two tuned retrieval configurations, plus fixed anchors. Evaluate 300 selection probes at 8k; compute the family-balanced frontier. Keep at most one champion per family for confirmation, plus fixed anchors. Full-stream sustainability can reverse development rankings.

S5 · Replication and sealed confirmation

Before unsealing, freeze the deployment candidate, the strongest cheap comparator, all confirmatory contrasts, and the at-most-seven configuration set. Complete three builds for each learned configuration. Run 300 confirmation probes at 8k; add secondary 2k/32k curves and diagnostic repeated reads. No further tuning.

S6 · Decision report and engine handoff

Publish all results, unresolved intervals, costs, failures, and tested boundaries. Produce a conditional default recommendation and machine-readable configuration. Carry it into E4 actions, E5 native freshness/economics, and E6 live operation before treating it as a fully validated production choice.

11 / INFERENCE

The winning configuration must survive a new question set.

QuestionAnalysis contract
What is the observational unit?Probe outcome within related-entity group, within a store build. Macro averages family scores; learned builds are averaged with equal weight. Repeated readers are nested observations, not new facts.
How are differences estimated?Use paired outcomes on identical probes and matched source prefixes. Resample related-entity groups, preserving paired conditions and family scoring. Incorporate independent build replicates in a hierarchical bootstrap. Freeze 10,000 bootstrap draws and analysis RNG seeds; report build-wise scores alongside intervals.
How are interactions estimated?Difference-in-differences: e.g. [F5−F4 under T1] − [F5−F4 under T0]. Report the interval and all underlying cell means. Development models are exploratory; promote only named interactions to confirmation before unsealing.

P3 = preselected deployment candidate − strongest cheap comparator chosen on selection, both at 8k with the same reader Q*. Choose Q* and count any extra read block before unsealing. If identical, P3 is structurally N/A and the cheap strategy is the candidate.
Multiple comparisonsHolm control across applicable primary contrasts at familywise α=0.05. Additional superiority/noninferiority claims join a separately declared confirmatory family; use simultaneous or multiplicity-adjusted one-sided bounds for deployment claims. Exploratory grids retain effect sizes and clearly labeled exploratory intervals.
SuperiorityPositive adjusted lower bound establishes improvement. A ≥0.05 macro gain is the proposed practical-relevance target, not an automatic quality threshold. Report exact effect and interval even if smaller.
Cost-based substitutionProposed noninferiority margin δ=0.02 macro against the chosen quality reference, plus no >0.05 loss on temporal or update accuracy. Use adjusted lower bounds, not “interval includes zero.” Margins must be justified from application needs and frozen before scoring; display stricter δ=0 and δ=0.01 sensitivity.
What is inconclusive?If intervals permit both material gain and material loss, do not declare equivalence. Retain the simpler incumbent provisionally or collect new independent data. Never relabel the same confirmation questions as a new test set.
Sample sizeUse development data to simulate paired group/build variability and CI width for P1–P3 and the 0.02 margin. Start at 300 confirmation probes, but increase before sealing if precision is inadequate. Three builds estimate gross instability, not exact variance.
Secondary binary testMcNemar only for declared binary outcomes; it is supplemental and does not handle entity clustering or the mixed exact/F1 macro. Do not silently threshold F1 to create the headline test.
Family balance / missing dataRequire supported population counts before freezing. Model failures score zero. A proven gold defect is documented, adjudicated blind, and removed from all arms; report the original count and affected conclusions. No store-specific exclusions.

Selection rule, frozen before selection scores

  1. Discard configurations only for gate failures that make comparison uninterpretable, such as future-data access or wrong input corpus. Ordinary poor quality and expensive operation are results.
  2. Within each family, retain its quality leader, its cheapest candidate with selection evidence consistent with the declared margin, and any candidate with a unique temporal/update advantage. Cap at 3 files, 2 graphs, 2 retrieval settings using macro, then measured query cost, then build cost as deterministic selection ordering. This is not proof that close candidates are equivalent.
  3. After full-stream selection, choose one champion per family. Choose a deployment candidate based on the declared workload profile and a conservative quality/cost assessment. Retain all four fixed anchors.
  4. Write PREREG-E3-confirm.md with exact candidate hashes, reader recipes, comparator, planned tests, and replicate counts. Complete all replica builds before opening confirmation.
  5. Confirmation evaluates the already selected candidate. If it fails, report failure/inconclusive. Another contender may be described as promising, but is not crowned through unadjusted selection on confirmation data.

17 / BOUNDARIES

What still needs a real input, and what E3 will not claim.

Required before actual runs

  • Dollar ceiling and wall-time ceiling for pilot, development, and full builds.
  • Available model/provider bindings and permitted execution credentials.
  • Two annotators and a scheduled gold-review session.
  • Observed support for grouped 300/300 probes and precision adequate for the chosen margins.
  • Deployment workload: expected queries per event horizon, freshness SLO, and tolerated quality loss.

These are explicit unresolved inputs, not hidden assumptions. They do not prevent creating this design artifact; they prevent falsely treating it as a completed preregistration.

Outside the core claim

  • Universal best storage, template, prompt, or model.
  • Unrestricted semantic explanation quality or coding-task success.
  • Database durability/concurrency/throughput superiority.
  • Live fast-lane benefit or a production-ready cadence.
  • Adaptive query/model routing, prompt-injection security, or cross-tenant access-control assurance.
  • Generalization to other organizations without replication.

Use the existing E4/E5/E6 work and a later project replication to address the relevant deployment questions.

Predictions should not drive tuning: record this artifact’s hypotheses before inspecting selection/confirmation results. The strongest plausible outcome may be a simple deterministic state store with hybrid search. Another plausible outcome is temporal files winning only for update-heavy questions, or graphs helping links without repaying their extraction costs. All support a useful, scoped engine design.
